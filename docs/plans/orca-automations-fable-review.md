# Fable review — `docs/specs/orca-automations.md` (branch axatbhardwaj/schedules-research, commit 9ee725f)

Reviewed against: `docs/specs/v1.md`, `docs/workflows.md`, `skills/axstack-relay/SKILL.md`, `skills/axstack-watch/SKILL.md` (+ `references/watch-runtime.md`, `references/repair-publication.md`), `skills/axstack-review/SKILL.md`, `skills/axstack/references/{run-record,contracts,lifecycle,orca-runtime,routing}.md`, `profiles/presets/mixed.json`, and the read-only help of `orca automations {create,edit,run,runs,show}`, `gh search prs`, `hermes send`. The settled decisions (two native automations, self = gh login, keyboard-equivalent own-PR authority, request/mention-only peer review, allowlist, prohibited operations, auditor-role gate, three criteria, both-reviewer recommendation, native `hermes send`) are taken as fixed and are not questioned below.

## Verdict

AGREE-WITH-AMENDMENTS — the design is sound and buildable, but as written it pushes a repair before the gate, lets a `proceed` override a validated security finding, cannot wake on a CI failure, and contradicts the still-active watch hold and the review skill's submission rule; amendments 1–9 must land before enabling.

## Required amendments

1. **Repair is pushed before review and before the gate (spec:47–49).** "a repair candidate that is pushed to the PR branch, then reviewed (below)" conflicts with `docs/workflows.md:118–121` ("Repairs return to the original author and receive refreshed authored review before scoped `gh stack` publication"), `skills/axstack-watch/references/repair-publication.md:78–81` ("Publication stays held until the current authored review receipt covers the exact new revision"), and the spec's own gate (spec:56–62), which becomes advisory if the mutation already happened. This is also the largest safety hole (area 4). Amend to: repair candidate is committed locally, reviewed and gated at its local SHA, and pushed only after `proceed`; the publication readback in repair-publication.md §3 runs immediately before the push.

2. **`proceed` can override a reviewer's validated security finding (spec:59–62).** "Reviewer 'yes' is input, not a veto; the gate decides… `proceed` lets the run continue" conflates two decisions: whether to *notify* the user (settled: the gate decides) and whether the *mutation may proceed*. Under `skills/axstack/references/contracts.md:69–76` and `docs/specs/v1.md:173–175` a credible serious-risk finding holds dependent dangerous actions and "disagreement… is not permission"; under `skills/axstack-review/SKILL.md:164–168, 238–241` a validated blocking finding returns to the author, never to publication. Amend: `proceed` means only "do not notify"; a push or `COMMENT` publication additionally requires no unresolved validated blocking finding, and a reviewer security "yes" that the gate does not escalate must be recorded as rejected-with-evidence or returned to the author before any mutation.

3. **Precheck cannot observe the event the own-PR watch exists for (spec:42–45).** The fingerprint is "PR number, head SHA, latest review-request and mention event IDs". A CI check completing or failing changes none of these and does not bump the PR's `updatedAt`, so a red check at an unchanged head never launches a session; the own-PR branch (spec:47) is unreachable on quiet ticks. Amend the fingerprint to include, per own PR, the check rollup state for the head SHA (`gh pr checks <n> --repo <r> --json state,name` or `gh api repos/{r}/commits/{sha}/check-runs --jq` hashed). See optional 1 for the simpler fingerprint that also removes the need for event IDs in the precheck.

4. **The spec creates schedules that the installed skills forbid (spec:38–41, 69–71).** `docs/workflows.md:157–167` ("Create no production schedule… Watch activation… remain held"), `skills/axstack-watch/SKILL.md:63–64`, `skills/axstack-watch/references/watch-runtime.md:23–36`, and `skills/axstack/references/lifecycle.md` "Watch health" all state an active hold, and the automation session will load these files. Amend: the spec must state that it lifts the native-watch hold by user decision, name the files to update in the same change (workflows.md, watch-runtime.md, lifecycle.md Watch health, axstack-watch SKILL.md §3, the `axstack-monitor`/`axstack-watchdog` role notes in all three presets), and re-state the accepted monitoring contract in its new shape (the driver automation is a mutating owner, not the "independent read-only monitor" of `watch-runtime.md:8–15`).

5. **Own-PR repair review mode is undefined and "both reviewers" contradicts authored mode (spec:47–49, 56).** "after both reviewers settle" and the settled "both reviewers must state an escalation recommendation" describe peer mode. An own-PR repair is authored mode: exactly one cross-family reviewer selected from actual author provenance (`skills/axstack-review/SKILL.md:86–102, 192–193`: "an authored receipt count other than one is not the selected mode"). The spec must say who authors the repair (the automation session itself, provider claude/Opus → `axstack-reviewer-primary` Sol medium in `mixed`; or a dispatched `axstack-author` Sol → `axstack-reviewer-secondary`), that the gate reads the one authored verdict in that case, and that "both reviewers" means "every mode-required reviewer".

6. **`COMMENT` publication has no rule in the review skill and no INCOMPLETE handling (spec:50–52).** `skills/axstack-review/SKILL.md:261–264` allows submission only "for a complete `APPROVE` or `REQUEST_CHANGES` verdict", both of which the spec prohibits; `SKILL.md:164–167` makes unresolved material reviewer disagreement `INCOMPLETE`. Amend: add a `COMMENT` submission branch (owner-synthesized, bound to the reviewed commit, both receipts current for the head SHA, readback of head/base before submit per SKILL.md:265–276), and state that `INCOMPLETE` or an unavailable required reviewer records a hold and publishes nothing.

7. **The gate cannot escalate anything the watchdog or the safety holds produce (spec:63–64 vs 76–77, 92–94).** The criteria are closed ("only these": security, on-chain, architectural), so "A finding is passed to the same gate" and "the gate decides whether to escalate" for a model mismatch or reused-session fallback are vacuous; the result is a permanent silent hold, which `docs/specs/v1.md:100` says "requires the user's decision". Amend with one of: (a) add a fourth, non-review criterion "automation health or model-substitution hold" usable only by the watchdog and the safety-hold path, or (b) state explicitly that those holds are recorded-only and surface when the user opens Orca. (b) is consistent with the settled criteria but should be a conscious choice in the spec, not an accident. Either way, define the dedup key for non-PR findings (finding type + first-observed run id); the current key "(PR, criterion, head SHA)" (spec:88) does not cover them.

8. **Gate or reviewer unavailability is undefined (spec:56–62).** If `axstack-auditor` (Luna) or a required reviewer is unavailable, `skills/axstack/references/contracts.md:37–43` says pause and ask the user with no fallback, but the only route to the user is the gate. Amend: an unavailable gate or reviewer records a hold, pauses mutation for that PR, and is treated as a watchdog health finding (and thus follows whatever amendment 7 decides).

9. **The relay skill needs a recorded `Notification policy` that the spec never creates (spec:15–17; `skills/axstack-relay/SKILL.md:26–28`).** Automated notifications are authorized only by "the caller's recorded `Notification policy`"; without it the skill keeps the message in the Orca conversation. Amend: the run record's `Notification policy:` line must read, verbatim in the automation prompt, something like `hermes send, target telegram (home), host VPS, gate-authorized escalations only`, and every message must say where the user acts (Orca conversation / worktree / PR) per `SKILL.md:69–71`.

10. **Acceptance 6 is not falsifiable as written (spec:111–113).** A real run cannot be forced to produce both `escalate` and `proceed`, and a model's judgment is not deterministic evidence (`docs/specs/v1.md:146`). Split it: (a) brief-format check — the gate, given a synthetic pair of verdicts, returns exactly one of the two literal tokens; (b) a run record carrying a recorded `escalate` decision produces exactly one relay receipt with state `sent`; (c) a recorded `proceed` produces zero. Also align the field name: spec:54 says `Escalate to user: yes | no — criterion — reason`, spec:111 says `Escalate: yes — security`.

11. **Acceptance 2 and 3 depend on `orca automations run` honoring the precheck, which the CLI help does not state (spec:104–107).** `orca automations run <id>` has no precheck flag; whether a manual run executes the precheck is unverified. Amend: test the precheck by executing the stored command directly and asserting its exit code on quiet and changed states; define "no duplicate work" observably as zero new pushes, reviews, or relay receipts on GitHub/Hermes readback and an unchanged record apart from `Updated:`.

12. **Model and effort cannot be set on the automation (spec:41).** `orca automations create --help` exposes `--provider` only; no `--model`/`--effort` flag exists, matching `watch-runtime.md:26–28`. Amend "model Opus, effort medium" to "requested via provider default (or `--source-context` if it carries model, to be verified); the per-run effective-model check is the enforcement", and note that `launch.requested`/`launch.effective` (spec:92–93) are not field names visible in `orca automations runs --help`; the spec must cite the actual run-history or session-inspection field once known, or the watchdog check is unimplementable.

13. **Run identity and cursor location are ambiguous for a shell precheck (spec:42–45, 79–85).** The record is `<git-common-dir>/axstack/runs/<UTCdate>-<slug>/progress.md`, Markdown written by the model. A precheck that "compares… with the run record's processed-event cursor" must parse prose. Amend: pin one run id for the lifetime of the automation (e.g. `20260916-pr-automations`) and keep a machine-readable sidecar (`cursor.json` or a one-line fingerprint file) in the same run directory, written by the driver after each processed tick; the precheck reads only that file. The driver stays sole writer of `progress.md`.

14. **Overlapping ticks (spec:40–41).** A repair plus two reviews plus a gate exceeds five minutes. With `--reuse-session` a new tick "submits later runs to the previous live automation session", i.e. queues a second prompt into a busy session, which can produce a duplicate writer for the same PR (`docs/workflows.md:82–84`). Amend: the precheck also exits non-zero while the previous run of A is still active (from `orca automations runs --id … --json`, once its status field is confirmed), or the spec cites verified native overlap suppression.

15. **Expired PRs are not excluded from later ticks (spec:65–67).** After expiry the PR still matches `author:@me`, so a later push re-fingerprints and the driver would re-adopt it, which is silent renewal (`docs/workflows.md`, `axstack-watch/SKILL.md:118–121`). Amend: the record marks the PR `expired`; the driver skips it until the user re-arms it in the automation session; state what the precheck does with such PRs (ignore them in the fingerprint).

16. **`gh stack` may rewrite history (spec:35–36 vs `repair-publication.md:94–96`).** The skills publish through `gh stack`; the spec prohibits force-push and rebase. State that repairs are pushed fast-forward to the PR branch only (`git push` with no lease/force), and that any `gh stack` sync or restack is out of scope for the automation.

## Optional improvements

1. **Simpler precheck fingerprint.** Replace "latest review-request and mention event IDs" with the search's own `updatedAt` per PR (`gh search prs --state open --author @me|--review-requested @me|--mentions @me --json url,number,repository,updatedAt`) plus own-PR head SHA and check-rollup state. Review requests and comments both bump `updatedAt`; event-ID dedup then belongs to the model in the session, where the record already stores it. This removes per-PR timeline calls from the precheck and keeps it under a small `--precheck-timeout` (set it explicitly, e.g. 60 s).

2. **Distinguish "nothing changed" from "gh failed" in the precheck.** Both exit non-zero and both look like a skipped run. Have the precheck append one line (`ts outcome`) to a `precheck.log` in the run directory; the watchdog flags N consecutive errors. Otherwise a broken `gh auth` on the VPS is indistinguishable from a quiet week.

3. **Remote targeting is confirmed but unstated.** The CLI supports `--environment vps` (saved environment id `37aa7ae2…`) with `--workspace <selector>`; the spec should say the automations are created against the VPS runtime this way rather than by shelling into the VPS.

4. **Drop the timezone.** `Asia/Kolkata` changes nothing for `*/5 * * * *` or `hourly`; it is one more field to keep in sync.

5. **Keep the driver worktree neutral.** `docs/specs/v1.md:70` wants one worktree per PR. If the automation's dedicated worktree checks out PR branches, two own PRs in one tick share a tree. Simplest: the driver never checks out a PR branch; a repair runs in a per-PR child worktree created through `orca-cli` and the driver's tree only hosts the record.

6. **State the automation session's roles once.** It is driver and owner for every PR it handles (no separate `axstack-owner` materialized), so `axstack-watch/SKILL.md:66–69` and `axstack-review/SKILL.md:62–69` "standalone owner" branches do not fire. This also keeps the run to one reused session.

7. **Allowlist location.** Put the allowlist in the automation prompt text (auditable via `orca automations show`) and say non-allowlisted PRs still receive report-only review (needed to judge a criterion) but no publication.

8. **Failed vs uncertain relay receipts.** The relay skill never auto-resends an `uncertain` attempt; a `failed` one may be retried once on the next tick. Add "unresolved failed/uncertain escalation receipt" to the watchdog's checks so a lost notification is at least recorded as a health finding.

9. **Session growth.** One session reused every five minutes for days accumulates context; state the expected reset (e.g. the user runs `--fresh-session` at will, and a fresh session reconciles from the record rather than treating itself as a fallback hold once per day).

## Confirmed sound

- **(1) Authority rules.** Self resolution via `gh api user --jq .login` matches `axstack-watch/SKILL.md:16–21`; keyboard-equivalent own-PR authority matches the "authorized maintenance" mode; peer-only-when-requested matches "Unsolicited reviews never happen" and peer read-only code; prohibited operations and human-merge default match `contracts.md:94–95` and `v1.md:28`. Contradictions found are listed above (amendments 1, 2, 4, 5, 6, 16), not here.
- **(2) Dedup rule for reviews.** "an event ID or a review receipt for an unchanged head SHA is never processed twice" is unambiguous for PR-bound work and matches `axstack-review/SKILL.md:169–176`. The gap is only for non-PR findings (amendment 7) and the cursor's physical form (amendment 13).
- **(3) CLI surface, verified parts.** `--precheck` "exit code 0 continues, anything else records a skipped run" matches the spec's inverted-exit semantics; `--reuse-session` is documented for existing-workspace automations, so `--workspace` + `--reuse-session` is valid; `--fresh-session` gives B its separate session; cron `*/5 * * * *` and `hourly` are accepted triggers; `--disabled` satisfies acceptance 1; `--environment vps` reaches the VPS runtime. `hermes send --to telegram --file <path> --json` and `--list telegram` exist exactly as the relay skill uses them, with exit codes 0/1/2.
- **(4) Gate flow, apart from amendments 1, 2, 7, 8.** Holds are cleared only by observation or the user (spec:97–98), which matches the relay skill's "silence never clears" and contracts.md; the watchdog never sends or mutates; unknown GitHub state blocks mutation.
- **(5) Precheck as a bounded shell command.** Feasible without a model once the fingerprint is the search output plus own-PR check state (optional 1) and the cursor is a sidecar file (amendment 13): three `gh search prs` calls, one `gh pr checks` per own PR, a hash compare, exit 1 on equal. `gh search prs` supports `@me` in `--author`, `--review-requested`, and `--mentions`.
- **(6) Simplicity.** The two-automation shape, one run record, no relay plugin, and no external scheduler are the minimum; nothing structural should be removed. Removable details are the timezone (optional 4) and event-ID collection inside the precheck (optional 1).

Unverified because the input is not installed locally: the Orca `references/automations.md` guide (run-history JSON fields, manual-run precheck behavior, overlap handling). Amendments 11, 12, and 14 depend on it and should be re-checked on the VPS before enabling.
