## Required amendments

1. **Wake for due control work, not only changed GitHub state.** Spec:103–110, 124–128, 154–164, 189–190 conflict internally and with `skills/axstack-watch/SKILL.md:115–121` and `docs/specs/v1.md:209`: the precheck skips an unchanged fingerprint, but the skipped driver alone expires watches and retries failed relay receipts. **Inference:** a quiet open PR can pass its deadline indefinitely without the required expiry/handoff transition; forcing a manual run does not demonstrate that scheduled expiry works. Specify a due-deadline/pending-control-work condition that can admit a bounded maintenance tick even when GitHub is unchanged, retaining overlap protection and unknown-state mutation holds. Store machine-readable deadlines and pending work in the sidecar, distinguish observation from completed processing, and recheck the deadline before publication if work spans it. Add acceptance with unchanged GitHub state crossing the deadline through the actual scheduled/precheck path, plus one due failed-send retry without a PR change. Ordinary quiet ticks must still skip.

2. **Complete the watchdog-to-owner notification path, including degraded operation.** Spec:71–79, 89–90, 133–142 and 146–156 conflict with one another and with `skills/axstack-relay/SKILL.md:98–102` and `skills/axstack/references/run-record.md:36–49`: B is read-only and never sends, only A writes the record, A can be stuck or prevented from running by `gh` errors, and no consumer/sender is named for B's gate result. The general gate procedure also assumes PR reviewers and a candidate, neither of which an automation-health finding necessarily has. **Inference:** detecting a broken A does not currently establish a path to an authorized notification or recorded receipt. Specify the health-gate input, durable native Orca delivery, authorized owner that consumes/sends/records it, and how that work is serviced independently of GitHub-change detection while preserving one writer and B's no-send rule. Define the failure thresholds, including N, and distinguish successful quiet prechecks from absent/unhealthy ticks. If the auditor gate itself is unavailable, explicitly retain the hold and expose the gap in Orca without a substitute or unauthorized send; referring the finding back to the same unavailable gate is not a completed escalation. Acceptance must exercise a real B health finding with A unable to run normally, not only a pre-populated `escalate` record; an unavailable gate and failed/uncertain delivery must remain visibly held. Any unsupported native delivery/recovery boundary remains a named enabling blocker.

3. **Name and reconcile all affected execution contracts, not only the native-watch hold.** Spec:15–21, 31–34 and 112–123 conflict with `skills/axstack-review/SKILL.md:73–77` (remote confirmation before reviewer dispatch), `docs/specs/v1.md:72–79` and `docs/workflows.md:108–121` (publication through `gh stack`), and `skills/axstack-review/SKILL.md:261–276` (submission only for complete APPROVE/REQUEST_CHANGES). **Verified:** the current spec correctly requires local review before a fast-forward push and commit-bound COMMENT submission, but its same-change update list does not explicitly reconcile these additional contracts. Add a narrowly scoped automation exception/update for local immutable-candidate review before push, fast-forward-only publication, and COMMENT submission with the existing remote readback and ambiguity handling; preserve ordinary workflows elsewhere. Clarify that the APPROVE/REQUEST_CHANGES prohibition is on GitHub actions, not the review skill's internal verdict vocabulary. Also reconcile spec:71 with `skills/axstack/references/contracts.md:71–76` and `skills/axstack-review/SKILL.md:218–230`: credible serious risk must immediately produce an internal prompt and dependent-action hold while gate-authorized external notification retains the settled gate policy. Acceptance should execute the loaded revised skills, so a prompt does not silently depend on ignoring conflicting instructions.

4. **Deduplicate completed work using the current review context and health episode.** Spec:104–107 and 160–164 conflict with `skills/axstack-review/SKILL.md:169–185` and `skills/axstack-watch/SKILL.md:78–99`. **Verified:** current base changes invalidate review evidence, and new CI/review events are actionable independently of head changes; the spec's unconditional unchanged-head receipt rule can suppress both. Its non-PR key also uses a single lifetime run ID (spec:146), which cannot distinguish a resolved health failure from a later recurrence of the same type. Specify per-PR observation/event state sufficient to identify changed work, reuse reviews only after validating candidate, current base and applicable scope, and do not let an existing review receipt suppress a new CI failure or request. Include base changes in the relevant change-detection path rather than assuming search `updatedAt` captures them. Give each health episode a first-observed occurrence identity distinct from the lifetime Axstack run ID, retaining dedup while unresolved. Acceptance: same head/new CI failure; same head/new base; duplicate event; and resolve-then-recur health failure. Each must produce exactly the intended new work or suppression.

5. **Bind model checks to effective runtime evidence before affected actions.** Spec:97–100, 135–140, 168–170 and 183–185 need an explicit evidence source and timing under `skills/axstack/references/contracts.md:39–43` and `docs/workflows.md:64–68, 78–81`. **Verified:** `orca automations create --help` exposes provider selection, not model/effort flags; a driver-written model label alone is not effective-session proof, and B is also a provider-default automation despite its configured watchdog role (`profiles/presets/mixed.json:140–146`). Require actual session/runtime inspection for A and B, record the effective identity, and treat unavailable/unknown evidence as a hold on affected work. A must validate before repair or publication rather than relying on the next hourly comparison; B must validate before its gate dispatch. Preserve role/preset launch validation for reviewers and the auditor. Exact runtime fields can remain an implementation-time verification item before enabling, but acceptance must cover correct, wrong and unknown effective identities and prove the affected actions remain held.

6. **Make discovery complete and candidate selection explicit.** Spec:35–40 and 103–111 conflict with the inspected `gh search prs --help`, which defaults to at most 30 results per search and describes `--mentions` as a user-mention filter, not a request-for-response filter. **Verified:** the supplied 18/8/7 counts fit today's per-query default; they do not establish future completeness or that mention matches request a response. Specify complete retrieval or an explicit detectable truncation hold, canonical dedup across the three searches with own-PR precedence, and verification of the qualifying request/comment before peer review. A historic or incidental mention is discovery data, not review authority. Add a fixture above the default result cap and one incidental mention, proving no silent omission and no unsolicited review; do not turn a discovery-capacity problem into permission to process arbitrary external content.

## Driver proposal

AGREE — record-only discovery outside the allowlist avoids model expense for repositories where the automation has no authorized publication or repair outcome, supported by the supplied VPS observation that nearly all 18 own PRs, 8 review requests and 7 mentions are external.

Replace spec:43–44 and carry the boundary through precheck/run/acceptance: record minimal external PR metadata in the bounded shell discovery step, exclude it from review/watch/gate dispatch and the model-work wake fingerprint, and never escalate on external PR contents. An external-only change should record discovery with zero review/model launches attributable to it and zero notifications. This is a deliberate coverage reduction: those repositories receive no security or architecture assessment, rather than an implied clean review. Automation-health errors affecting discovery itself remain within the fixed health criterion. The current spec says “each changed PR,” so the measured counts are a workload-exposure argument, not proof that approximately 17 full external reviews execute every five minutes; query overlap and actual token cost were not measured.
