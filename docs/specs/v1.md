# Axstack v1 — approved specification

Status: approved implementation baseline. Scope was approved before
implementation and amended for the Bun >= 1.3.14 runtime. Implementation
issues #2 (installer) and #3 (workflows) were opened under the approved
scope.

This issue is the specification for building Axstack. Axstack itself uses GitHub Issues for this project; the toolkit retains its Linear-first integration and explicit repository Markdown option.

## Purpose and product boundary

Axstack is a public, standalone toolkit for finishing agreed engineering work with less supervision while retaining independent cross-model review. It owns alignment, specification, ticketing, execution, and review without requiring Matt Pocock's or Poteto's skills to be installed.

Users invoke skills from chat. An installation/setup CLI bundles and installs those skills and checks configuration; it is not a second agent runtime or the user's execution interface. Paseo owns sessions, workspaces, delegation, notifications, schedules, and heartbeats.

The first release targets Linux and macOS, with Windows through WSL. GitHub through `gh` and the `gh stack` extension is the initial forge. Claude, Codex, OpenCode, and Grok are compatibility targets; Claude and Codex are the initial everyday harnesses. A compatibility claim requires evidence for the actual adapter, model configuration, skill loading, and tools. An installable skill alone is not proof of end-to-end support.

## Agreed user journey

1. Start Axstack in chat, or invoke a phase directly with its required inputs.
2. The driver interviews the user, resolves factual questions, and produces a specification with observable acceptance criteria and explicit exclusions.
3. The user approves the spec. The approved revision is the execution baseline.
4. Axstack creates capability tickets, decomposes them into internal tasks, and executes without routine confirmations between phases.
5. Persistent PR owners arrange implementation, verification, independent review, repairs, and delivery of reviewed PRs or a reviewed stack.
6. The human merges by default, bottom-up for a stack. A run may receive explicit merge authorization; review approval itself never grants that authority.
7. Axstack monitors delivered work for a configurable 24 hours, ending earlier when all required PRs merge. Work remaining at expiry receives a resumable handoff rather than silently renewed monitoring.

Material scope changes, required model substitutions, and serious-risk decisions are explicit exceptions to autonomous progress. Holds apply to affected work; independent safe work may continue.

## Specification and ticket storage

Linear is the default selected integration, with repository Markdown an explicit alternative.

- In Linear mode, the authoritative spec is a native Linear document. Before use, check the actual session's required MCP tools and access. Missing access is a setup gap, not permission to silently switch stores.
- Linear issues represent high-level, user-visible capabilities. One capability may span several implementation tasks and PRs. Detailed execution breakdowns live in the repository.
- The driver owns every Linear mutation. A small, inexpensive sync agent only reports discrepancies in issues belonging to the run, with supporting evidence.
- A reviewed but unmerged capability stays In Review. Done requires all required PRs to be merged and the capability's acceptance checks to pass.
- If the approved spec changes materially, identify affected work, propose the revised scope and plan, and hold affected code changes until the user accepts them. Preserve the previous approval baseline while resolving the change.

Proposed representation: keep a repository snapshot of the approved spec revision and concise task/decision records, with the Linear document identified as authoritative. Keep machine-specific session identifiers and temporary operating records out of public commits. These are supporting artifacts, not an independent workflow database.

## Hosts, ownership, and parallelism

Each run stays on one Paseo execution host. A server and desktop can host separate runs; other devices can be interaction and monitoring clients. Multiple providers can execute on one host. Automatic migration or splitting a run across hosts is outside v1.

The default is two active PRs per run, configurable per host. This is a PR concurrency limit, not a two-agent limit: authors and reviewers add sessions. The driver queues dependent or conflicting work instead of launching every ticket at once.

Each PR has one persistent Opus owner. That owner may delegate coding and launches its own independent reviewers. It remains accountable for its candidate, fixes, verification evidence, and monitoring. The main driver owns overall scope, cross-PR dependencies, stack coordination, and capability completion.

Each PR uses its own worktree. Exactly one agent has write ownership of a particular candidate at a time. An owner handing coding to a worker does not simultaneously edit that worker's files. Reviewers inspect an immutable candidate in independent checkouts. Worktrees isolate file edits, not ports, shared databases, credentials, or all Git metadata; those resources need appropriate setup and coordination.

Dependent PRs build on reviewed parent candidates. The main driver coordinates stack topology through `gh stack`. Parent changes invalidate affected descendant evidence and require the relevant update and re-verification. A green parent does not prove that a combined stack works.

## Model roles

The selected main chat remains the driver; Astra low is the preferred starting selection. There is no implicit handoff or global model change.

| Role | Starting routing |
| --- | --- |
| Main driver | Current chat; Astra preferred |
| Consequential planning advisor | Fable medium |
| Persistent PR owner | Opus medium |
| Ordinary implementation and repairs | Sol medium |
| Independent Opus review | Fresh Opus medium session |
| Second independent final PR review | Fresh Sol medium session |
| Linear discrepancy checker | Explicitly configured inexpensive model; selection still open |

The driver consults Fable for consequential decisions still unresolved after factual checks, not every task or phase. The proposed preset additionally requires Fable's plain AGREE and the driver's accepted assessment for high-stakes decisions. The ordinary implementation pair is Sol medium / Opus medium; the high-stakes pair is Opus high / fresh Sol high. Preserve these distinctions in the proposed Axstack preset, while retaining the agreed two-reviewer final PR contract.

Models and effort settings are configurable and checked at setup and launch as appropriate. An unavailable or exhausted model pauses affected work and requires the user's decision before another model is used. No automatic fallback, including one listed in configuration. Preselected roles for different task classes are distinct from substituting a model after a failure.

The PR owner is not its own independent reviewer. Implementation checkpoint review and final review should reuse eligible reviewer sessions where evidence and scope allow, rather than automatically adding a third final reviewer. Authoring disqualifies a session from independently reviewing that candidate; using the same model family in a fresh non-author session is allowed.

## Strict TDD and verification

Every implementation follows red → green → refactor. Define a meaningful behavior check, execute it and observe the intended failure, implement the smallest change that satisfies it, then refactor while keeping checks green. Tests written only after implementation do not satisfy the requirement.

Checks derive from approved acceptance criteria, failure behavior, and actual integration boundaries. They must not merely restate source text or mirror the implementation. For skill behavior, use representative task scenarios with predeclared expected outcomes; for configuration, test its observable effects. Do not describe nondeterministic agent evaluations as deterministic proofs.

Capture concise evidence of the failing and passing checks and the candidate they concern. Independent review checks TDD evidence, test adequacy, design, and acceptance coverage. A test passing is not enough if it checks the wrong behavior.

UI work additionally requires rendered interaction evidence when relevant; integration and infrastructure behavior require checks of the affected boundary. These checks supplement TDD. Missing prerequisites or a test that failed for an unrelated setup problem must not be represented as the intended red result.

Proposed exception handling: if meaningful test-first verification cannot be established, report the limitation and ask for a scoped decision before dependent implementation. Do not silently waive strict TDD or fabricate a test to satisfy a checklist.

## Two-reviewer contract

Each PR owner launches exactly two independent final reviewers, Sol and Opus by default, with the same instantiated scope, spec, ticket, base, candidate revision, exclusions, and review instructions. Neither reads the other's initial findings or creates children.

Both cover all six angles:

1. Security and trust boundaries.
2. Correctness, failures, and edge cases.
3. Integration and regressions.
4. Requirements, acceptance, and user behavior.
5. Architecture and solution design, including SOLID and credible simpler alternatives.
6. Simplicity and maintainability: KISS, YAGNI, and cyclomatic complexity where measurement is useful. Never invent a metric or demand abstractions simply to satisfy a principle.

Reviewers report concrete evidence and consequences, coverage, limitations, and findings tied to the candidate. No finding quota. The owner verifies findings, reconciles contradictions with focused checks, and returns accepted fixes to the author. Unresolved material disagreement means incomplete review; votes do not settle correctness.

Changes require a refreshed review receipt for the new revision. Reuse unchanged evidence and review only the delta plus affected behavior when sufficient; substantive scope, base, or behavior changes require broader review. Neither reviewer unanimity nor passing tests grants merge authority.

## Prompt-only urgent escalation

Credible serious security issues, possible infrastructure downtime or data loss, and major design concerns are raised immediately. Do not wait for the second reviewer or consensus.

The owner/driver holds approval, merge-ready declarations, and dependent dangerous actions while presenting the evidence, likely impact, available options, and needed user decision. Safe investigation and unrelated work may continue. Disagreement or lack of response is not permission to proceed.

This is an instruction in the skills and briefs, not a new programmatic gate, hook, or decision engine. Hermes bot relay is an optional configured notification route that respects its existing authorization requirements. Paseo chat is the fallback; failed notification delivery never resolves the concern. Public installations must not inherit private host paths, recipients, credentials, or personal relay configuration.

## Monitoring and recovery

PR owners remain responsible for their PR during the configured monitoring window. Wake work when CI/review state changes or when a bounded scheduled check is due; do not keep models reasoning continuously while waiting. Existing Paseo mechanisms own those wake-ups.

On restart or resume, reconcile recorded ownership with actual Paseo sessions, Git revisions, GitHub state, and the approved spec. Reuse existing owners and workers where appropriate; do not spawn replacements merely because context was lost or a notification was ambiguous. Report unresolved launch state before creating a duplicate writer.

The Linear checker reports only run-scoped discrepancies. The driver independently verifies evidence before applying updates. Spec/acceptance changes and conflicting state are decisions, not routine sync repairs.

## Proposed package boundaries

These are implementation proposals for review, not previously selected product decisions:

- One standalone repository and versioned package, self-contained for new users.
- Owned skills for the entry workflow, alignment, specification, tickets, implementation, review, and monitoring; shared references define ownership, evidence, and escalation once.
- Small installer modules for harness installation locations, Paseo profile configuration, and capability checks. Preserve unrelated profiles, credentials, schedules, and user files; update/uninstall only Axstack-owned assets.
- Progressive skill loading so a task receives the applicable phase and concise source-linked brief rather than every workflow instruction.
- Explicit compatibility records distinguish local checks, controlled simulations, and actual end-to-end harness runs.
- No separate Axstack daemon, multi-host scheduler, mandatory planning panel, or dependency on upstream Matt/Poteto skills.

Borrow Matt's user alignment and spec-to-ticket discipline, and Poteto's accountable PR ownership, bounded delegation, artifact-based verification, and dependency-aware parallelism. Mandatory large panels and nested coordination are not imported.

## Release acceptance scenarios

1. A clean supported environment installs the owned skills, checks required tools, and starts from chat without Matt's or Poteto's bundle.
2. Missing Linear document access produces an actionable setup gap; explicit Markdown mode works independently.
3. One approved capability becomes internal tasks and a two-PR stack; owners remain distinct and each candidate receives independent Sol and Opus coverage of all six angles.
4. A behavioral implementation demonstrates a real red/green/refactor sequence, with a seeded regression and inadequate-test case detected by verification/review.
5. A changed parent invalidates affected child evidence; a material spec edit holds affected implementation while unrelated work continues.
6. Model outage, interrupted launch, reviewer disagreement, and serious-risk scenarios preserve holds and do not create duplicate writers or automatic model substitutions.
7. A reviewed unmerged capability stays In Review. The checker reports drift without mutating Linear; Done follows verified merges and passing acceptance checks.
8. Monitoring ends at the configured deadline or earlier completion, with resumable remaining work and no silent renewal.
9. Installation/update/uninstall preserves unrelated configuration and works on the claimed platforms. Runtime compatibility is reported only at the level actually verified.
